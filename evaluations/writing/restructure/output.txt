# Archive: file identity, access, and deletion

Archive accepts uploads, keeps their original bytes for 90 days, and provides downloads through short-lived URLs. Three parts work together: intake validates and records an upload; storage keeps its bytes and metadata; delivery checks access before issuing a URL. A blob is the stored byte content. A metadata record describes a file’s owner and access policy. Separating them lets identical uploads share storage while retaining distinct file identities and permissions.

Several limits affect product promises. Customers must scan files for malware before upload because intake does not scan them. Access changes cannot immediately revoke issued URLs: each remains usable until its five-minute expiry. Deletion also has no tested completion-time guarantee, and backup expiry can take up to 14 additional days. Do not promise immediate removal of every copy.

## From upload to download

The upload endpoint issues a token valid for 15 minutes. Intake rejects files over 50 MiB, reads accepted bytes, computes a content hash, creates the blob if needed, and then creates metadata. The hash identifies content; the file ID identifies the recorded file. Successful intake returns a file ID only after both the blob and metadata are stored.

Suppose two owners upload matching content. Their uploads receive different file IDs but use one stored blob. Each metadata record carries an owner ID, an access policy version, and a created-at time in UTC. Owners cannot change the content hash. Metadata can change independently of the stored bytes, so a policy update does not require another upload.

For a download, the API checks the current metadata access policy and issues a URL valid for five minutes. The URL identifies the blob without exposing the owner ID. This connects the separate identities: the file’s metadata controls whether a URL can be issued, while the resulting URL points to the shared byte content. No supported bulk-download endpoint exists.

## What changes can and cannot do

A policy update affects later download requests, but an already issued URL keeps working until it expires. An admin can disable new URL issuance for a file; previously issued URLs can still work for up to five minutes. Both controls therefore restrict future issuance without immediately stopping access through existing URLs.

Deletion follows a different set of conditions. Only an owner or admin can request it, and legal hold blocks deletion even for an admin. Legal hold does not grant download permission: retaining content and authorizing access remain separate decisions.

Shared storage adds another deletion dependency. A blob can be deleted only when no metadata record references it. In the two-owner example, a remaining reference prevents blob deletion. Removing one file’s metadata therefore does not by itself establish that the shared bytes can be removed. Combined with the untested completion time and backup expiry, this limits what the product can promise about removal.

There is also a failure case during intake. If metadata creation fails after a blob is created, a cleanup task removes unreferenced blobs. Cleanup runs every hour. This addresses storage left without a file record; it does not establish a tested deadline for completing requested deletion.

## Authority, inspection, and the open decision

Use these authority rules when designing product actions:

| Operation | Authority |
| --- | --- |
| Upload | Account member |
| Change access policy | Owner |
| Request deletion | Owner or admin |

Legal hold blocks deletion even when the requester has authority. Blob removal also depends on all references being gone. Access policy changes remain subject to the lifetime of URLs already issued.

Inspect a file with:

```bash
archivectl inspect --file "demo 7" --format json
```

Support has requested instant URL revocation. The team has not decided whether to implement it. A proxy download endpoint is a possible design, but its cost and latency are unknown. Treat instant revocation as an unresolved requirement; current behavior permits existing URLs to remain usable until expiry.
