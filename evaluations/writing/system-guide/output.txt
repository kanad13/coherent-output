# Relay: an engineer’s guide

## Understand the complete event path

Relay accepts customer events through an HTTP gateway and makes stored events available through search. The path has separate stages: the gateway appends an event to a durable queue, workers normalize timestamps to UTC, attach a schema version, and write events to the durable store, and a separate indexer reads stored events and updates the search index. Search uses that index and filters results by tenant. Workers divert events with invalid timestamps to quarantine for operator inspection.

These stages establish different boundaries. HTTP 202 means the event reached the durable queue. It does not mean the event is searchable. A successful store write also does not ensure an immediate index update. The durable store retains normalized events for 30 days, while search visibility depends on the indexer’s updates.

Tenant identity connects acceptance, storage, search, and deduplication, which uses an event key to identify repeated deliveries. A tenant API key identifies the tenant at the gateway and is also required for search. Retried deliveries can produce duplicates, so a customer-supplied `event_id` matters. Deletion also crosses stages: Relay removes the stored event first, and the indexer removes its search entry later. A deleted event can therefore remain visible in search, and search absence is not proof of durable deletion.

## Follow an event from acceptance to search

Consider a customer sending an event with a tenant API key, a timestamp, and an `event_id`. Before queueing, the gateway rejects requests with missing tenant keys and events larger than 256 KiB. An accepted request receives HTTP 202 only after the event is appended to the durable queue. This is the acceptance boundary to use when interpreting the HTTP response.

A worker consumes the queued event, normalizes its timestamp to UTC, and attaches a schema version. An invalid timestamp changes the event’s path: the worker moves it to a quarantine queue. Operators inspect quarantine records; Relay does not support automatic correction. Quarantine is therefore a distinct outcome from writing a normalized event to the durable store.

For an event that proceeds to storage, the storage key includes the tenant ID. If the store write fails, the write is retried. The worker acknowledges its queue message only after a successful store write. This ordering connects queue processing to durable storage: the acknowledgment follows the write, rather than preceding it.

The indexer then reads stored events and updates the search index. In last week’s staging run, measured indexing lag ranged from 2 to 8 seconds. Production indexing lag has not been measured. The staging result describes that run; it does not establish a production timing guarantee. When explaining availability to a customer or investigating an event, distinguish queue acceptance, successful storage, and search visibility.

## Connect retries, identity, and retention

Retries matter beyond store-write recovery because retried deliveries can produce duplicates. Relay uses the customer-supplied `event_id` as its deduplication key. Without an `event_id`, an event can be stored more than once. HTTP acceptance alone does not resolve that duplicate risk.

Deduplication applies within a tenant for the 30-day retention period. Tenant identity is thus part of the deduplication boundary as well as the storage boundary. Keep both limits in view when reasoning about repeated events: the documented scope is one tenant and that retention period.

The same tenant boundary governs retrieval. Search requests require a tenant API key, and search filters by tenant ID before returning results. Cross-tenant search is unsupported. A storage key containing tenant ID and a tenant filter in search serve related roles at different stages of the event path.

Deletion introduces another delay between storage and search. Relay deletes the event from the durable store first. The indexer later removes its index entry, so a search result can persist after durable deletion. Conversely, an absent search result does not prove that durable deletion occurred. Search visibility and durable deletion must remain separate conclusions.

## Use operational signals at the relevant stage

Operators monitor queue age, store-write failures, quarantine size, and index lag. Each signal relates to a different part of the path: queued work, writes to storage, invalid timestamps awaiting inspection, or updates to search. There are no documented alert thresholds yet. The available signals establish what operators monitor, but they do not establish when an alert should fire.

Capacity changes also have stage-specific effects. The gateway and search service scale separately. More workers can reduce queue delay, but they do not necessarily reduce indexing lag. If the question concerns search visibility, a worker increase alone does not establish that visibility will improve sooner.

The evidence available to a joining engineer has clear limits: production indexing lag is unmeasured, and no pricing or production throughput measurements are available. Keep those gaps explicit in estimates and explanations. Use the documented stage boundaries to describe Relay’s behavior, and use the stated measurements only within their reported scope.
