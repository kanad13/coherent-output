# Archive: file lifecycle and product limits

Archive accepts files, preserves their original bytes for 90 days, and controls downloads through metadata. Intake validates an upload and creates the stored content and its metadata. Storage shares identical content between records. Delivery checks a record’s current access policy before issuing a temporary download URL. These parts connect through two identifiers: a file ID identifies a metadata record, while a content hash identifies matching content.

Three limits shape the product experience. Customers must scan files for malware before upload because intake does not scan them. Changing permissions cannot immediately revoke an issued URL: it remains valid until expiry, up to five minutes. Deletion also cannot promise immediate removal of every copy; completion time has no tested guarantee, and backup expiry can take up to 14 additional days.

## Follow a file from upload to download

The upload endpoint first issues an upload token valid for 15 minutes. Intake rejects files over 50 MiB, reads the bytes, and computes a content hash. It creates a blob—the stored bytes—if matching content is not already stored, then creates metadata. That metadata contains an owner ID, an access policy version, and a created-at time in UTC.

Successful intake returns a file ID only after both the blob and metadata are stored. If metadata creation fails, a cleanup task removes unreferenced blobs. This task runs every hour, so a failed intake can leave an unreferenced blob awaiting cleanup.

Consider two owners uploading identical content. Their uploads use one stored blob but receive different file IDs because each upload has its own metadata record. The shared content hash does not replace either file ID. This distinction matters throughout the lifecycle: permissions belong to metadata, while content sharing and eventual blob deletion depend on references to the bytes.

When either owner requests a download, the download API evaluates the current metadata access policy. If access is permitted, it issues a URL valid for five minutes. The URL identifies the blob and does not expose the owner ID. Delivery therefore uses metadata to authorize URL issuance, while the issued URL refers to the stored content.

## Separate permission changes from content changes

Metadata can be updated independently of the original bytes. Owners cannot change a content hash. An owner can change the access policy, and delivery evaluates that policy at download time. However, a URL already issued continues working until it expires even if the metadata access policy changes.

An admin can disable new URL issuance for a file. Previously issued URLs still remain valid for up to five minutes. Product flows that describe an access change must distinguish stopping future URL issuance from stopping access through URLs already issued.

Deletion has a separate authority boundary. Only an owner or admin can request it, and legal hold blocks deletion even for an admin. Legal hold does not grant download permission: retaining content and authorizing access are independent decisions.

Shared storage adds another deletion condition. A blob is deleted only when no metadata record references it. In the two-owner example, deleting one record cannot trigger deletion of the blob while the other record still references it. Combine this condition with the untested deletion completion time and backup expiry before making removal commitments.

## Boundaries for implementation and support

Archive keeps files for 90 days. The retention period is distinct from a guarantee about deletion completion or removal of backup copies. No supported bulk-download endpoint exists, so the documented delivery interface does not provide bulk downloading.

Support has requested instant URL revocation, but the team has not decided whether to implement it. A proxy download endpoint is a possible design; its cost and latency are unknown. Treat it as an unresolved proposal when discussing product behavior.

Use the inspection command when examining a file:

```bash
archivectl inspect --file "demo 7" --format json
```

The operation authorities are:

| Operation | Authority |
| --- | --- |
| Upload | Account member |
| Change access policy | Owner |
| Request deletion | Owner or admin |
